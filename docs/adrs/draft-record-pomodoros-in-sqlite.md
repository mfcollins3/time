# Record Pomodoros in a local SQLite database

## Context and Problem Statement

Naked Time runs a 25-minute countdown but keeps no history, so users cannot
review the time they have spent. How and where do we persist Pomodoros so that
completed, cancelled, and terminated Pomodoros can be told apart?

## Decision Drivers

* Pomodoros must be recorded even if the program is killed, so a Pomodoro
  cannot depend on a clean shutdown to be saved.
* A Pomodoro needs a stable public identifier that is safe to expose, separate
  from the internal key.
* Timestamps must be unambiguous (UTC).
* No extra runtime dependencies on any of the five release targets (see
  [Build and publish release binaries on native runners for five
  targets](draft-release-build-targets.md)).
* The schema will change over time, so upgrades must be handled.

## Considered Options

* SQLite with the bundled library (`rusqlite`), one row per Pomodoro
* SQLite linked against the system library
* An append-only text or JSON file

## Decision Outcome

Chosen option: "SQLite with the bundled library", because it needs no system
library, supports in-place updates and queries, and works on every target.

* The database is `$HOME/.naked-time/data.db` (`%USERPROFILE%\.naked-time\data.db`
  on Windows), resolved with `std::env::home_dir()`. The directory is created on
  first use.
* The `pomodoros` table has an `INTEGER PRIMARY KEY AUTOINCREMENT` `id` for
  internal use and a unique `public_id` holding a UUIDv7 as hyphenated text.
* `start_time` and `end_time` are ISO-8601 UTC text with millisecond precision
  (`2026-11-21T14:03:07.123Z`), generated by SQLite so no date/time crate is
  needed. The text form is readable in the `sqlite3` shell and sorts
  chronologically.
* The row is inserted when the Pomodoro starts. `end_time` is set only when the
  countdown completes, so a Pomodoro cancelled with CTRL+C or killed has a NULL
  `end_time`.
* The schema is versioned with `PRAGMA user_version`; migrations are an
  append-only list applied in a transaction at startup. The database uses WAL
  mode and a busy timeout.
* If the database cannot be opened, the program exits before starting the
  timer rather than silently losing the record.

### Consequences

* Good, because history survives crashes and kills, and the NULL `end_time`
  distinguishes incomplete Pomodoros.
* Good, because the public UUIDv7 is time-ordered and does not leak row counts.
* Good, because no runtime dependency is added.
* Bad, because bundling SQLite adds a C build step and increases build time and
  binary size.
* Bad, because the program refuses to run if `~/.naked-time` is unwritable.
* Bad, because the home directory is unavailable in rare environments (no
  `HOME`), which is also a startup error.

### Confirmation

Unit tests in `src/db.rs` cover migrations, UUIDv7 and timestamp formats, and
the NULL/non-NULL `end_time` behavior, and run in CI.

## Pros and Cons of the Options

### SQLite with the bundled library

* Good, because it is self-contained and cross-platform.
* Good, because it supports queries for future reporting.
* Bad, because it lengthens the build.

### SQLite linked against the system library

* Good, because binaries are smaller.
* Bad, because every platform needs a compatible SQLite installed, including
  Windows, and packages would gain a dependency.

### Append-only text or JSON file

* Good, because it is trivial to implement.
* Bad, because updating the end time of a record is awkward and not atomic.
* Bad, because reporting would need to parse the whole file.
